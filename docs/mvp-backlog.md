# План реализации купонного MVP

Статус: **MVP-01–MVP-06 реализованы в этой ветке; реальный пилот запускается отдельно**. `MVP-01` и другие обозначения — идентификаторы разделов этого плана, не номера уже созданных GitHub issues. Продуктовые правила находятся в [спецификации](coupon-mvp.md).

Каждая задача выполняется отдельным PR с необходимыми изменениями backend, frontend, контракта и проверок. Не создавать все будущие таблицы и интерфейсы в первом PR. Слияние и серверное развертывание — отдельные действия в рамках явно выданного разрешения.

## Порядок

| Задача | Результат для специалиста | Зависимости |
| --- | --- | --- |
| MVP-01 | Вход, выход и закрытый кабинет | Инфраструктурный каркас |
| MVP-02 | Добавление и поиск клиентов | MVP-01 |
| MVP-03 | Выдача, поиск и отзыв купонов | MVP-01; MVP-02 для привязки к клиенту |
| MVP-04 | Применение и отмена с проверкой всех ограничений | MVP-01, MVP-02, MVP-03 |
| MVP-05 | Компактная карточка, QR и публичная страница | MVP-03 |
| MVP-06 | Результаты пилота и проверка полного рабочего сценария | MVP-02, MVP-04, MVP-05 |

Текущий функциональный PR реализует **MVP-06**, результаты пилота и сквозную программную приемку. [Определения показателей](pilot-statistics.md) и [подготовка реального пилота](pilot.md) описаны отдельно. Детали QR, публичного API и печати — в [документации](public-coupons.md). В первой версии специалист вручную добавляет клиентов и отмечает применение купонов. Учет визитов, Google Таблицы, импорт и синхронизация отложены до появления подтвержденной потребности клиента. Полный сценарий пилота не требует этих функций.

## MVP-01 — вход специалиста и кабинет

Цель: специалист входит в приложение, получает доступ к своему кабинету и может завершить сессию.

Объем:

- Ввести команду запуска версионированных миграций и первые таблицы для учетных записей, сессий и ограничения попыток входа.
- Создавать первую учетную запись через явную административную команду; без фиксированного пароля в исходниках и открытой регистрации клиентов.
- Добавить вход, получение текущей сессии и выход в API и OpenAPI, экран входа и оболочку кабинета во Vue.
- Использовать серверные сессии с безопасным хранением пароля, сроком жизни, завершением при выходе и защитой изменяющих запросов от CSRF. Cookie и настройки разработки/HTTPS документировать.
- Ограничить попытки входа. Получать специалиста из проверенной сессии, не доверять переданному клиентом ID владельца.

Критерии приемки:

- [x] Чистая БД поднимается командами README; повторный запуск миграций не повреждает данные.
- [x] Корректные учетные данные открывают кабинет; ошибочные не создают сессию и не раскрывают секреты.
- [x] Защищенный API недоступен без сессии; чужой ID в запросе не меняет область доступа.
- [x] Выход и истечение сессии прекращают доступ, включая прямые API-запросы.
- [x] Секреты не попадают в логи или клиентскую сборку; настройки cookie/CSRF и ограничения попыток проверены.
- [x] Есть browser-сценарий «вход — кабинет — выход» и проверки существенных ошибок.

В этот PR не входят купоны, пациентские данные, интеграция CRM и публикация реального сервиса для пациентов.

## MVP-02 — клиенты

Цель: специалист находит существующего клиента или создает карточку, чтобы выбрать ее при применении купона.

Объем: собственные карточки клиентов с постоянным внутренним ID и владельцем, API и формы ввода, поиск и исправление контактных данных. Перед завершением задачи определить минимальные обязательные поля, валидацию и порядок исправления ошибок; отразить решения в спецификации. Учет визитов, интеграции и импорт файлов не входят в задачу.

Критерии приемки:

- [x] Клиента можно создать, найти и просмотреть внутри Referflow без Google-аккаунта, внешних ID или доступа к CRM.
- [x] Минимальные поля соответствуют спецификации; ранее исключенные поля `Посещение`, `НУЖНО УТОЧНИТЬ`, `Цена ₽` не собираются. Карточки изолированы по специалисту.
- [x] Клинические поля, исходные тексты, доход и дата рождения не сохраняются и не попадают в вывод ошибок.
- [x] Повтор одной отправки формы не создает дубликат. Изменение имени/телефона сохраняет внутренний ID и историю клиента.
- [x] Поиск существующих клиентов и подсказки о возможных дубликатах помогают избежать второй карточки; общий телефон родственников не вызывает автоматического объединения или запрета.
- [x] Невалидные данные формы и обращения к чужой карточке отклоняются; клиент не может задать себе другого владельца.
- [x] Создание новой карточки не устанавливает автоматически признак первого посещения.
- [x] Исправления/архивирование сохраняют внутренний ID; будущие применения и лимиты не должны обнуляться из-за изменения контактов.
- [x] Browser-сценарий «найти или создать клиента — изменить контакт — найти ту же карточку» проходит на искусственных данных без внешних сервисов.
- [x] Нет таблиц, API, форм, полей даты или скрытого автоматического создания визитов.

Доступ к внешней CRM не является условием приемки или запуска пилота. Не добавлять учет посещений, SDK, настройки подключения, фоновые задачи или пустые интерфейсы будущей синхронизации.

## MVP-03 — создание и отзыв купонов

Цель: специалист создает купон, видит его условия и счетчики, находит по короткому номеру и при необходимости отзывает.

Критерии приемки:

- [x] Есть процентная и фиксированная скидки, необязательные текстовые ограничения, срочный/бессрочный режим и оба типа допустимых посещений.
- [x] Общий и персональный лимиты независимо принимают положительное число или неограниченность. Персональный по умолчанию равен 1.
- [x] Купон самостоятельный: нет сущностей программы лояльности или кампании.
- [x] Создаются короткий номер и случайный UUIDv4. Короткий номер генерирует только система с проверкой уникальности; ручной ввод через UI/API запрещен, старые номера не переиспользуются.
- [x] Поиск, просмотр и отзыв изолированы по специалисту; массовый перебор ограничивается по инициатору запросов.
- [x] Отзыв окончателен и не уничтожает историю. Поиск и просмотр купона не расходуют лимиты.
- [x] До завершения задачи определены формат короткого номера, граница срока/часовой пояс, точность номинала и необходимость связи с рекомендателем. Выбранные решения явно отражены в спецификации и UI.

## MVP-04 — применение и отмена

Цель: специалист выбирает клиента и подтверждает применение купона без регистрации визита; ошибку можно отменить с причиной и сохранением истории.

Критерии приемки:

- [x] Автоматически проверяются существование клиента и купона, их владелец, отзыв, срок, общий и персональный лимиты.
- [x] Для купона только на первое посещение требуется явное подтверждение специалиста; оно по умолчанию отсутствует и сохраняется с автором/временем. Пустая история применений не считается доказательством первого посещения.
- [x] Специалист подтверждает отсутствие другого действующего купона на этот реальный прием; для сверки видит историю применений клиента. Интерфейс и документация не обещают автоматической проверки одного купона на визит.
- [x] Применение хранит клиента, купон, автора, серверное время операции и ручные подтверждения; `visit_id`, форма визита и скрытая запись визита отсутствуют. Нет несогласованного ограничения одного купона на клиента в день.
- [x] При конкурентных запросах лимиты не превышаются, включая персональный лимит при неограниченном общем.
- [x] Повтор одного запроса создает одну операцию. Одинаковый ключ с разными данными отклоняется; повтор после отмены не создает новую операцию самопроизвольно.
- [x] Отмена освобождает оба лимита ровно один раз. Замена ошибочного применения требует явной отмены и отдельной новой операции; соблюдение правила одного купона на прием проверяет специалист.
- [x] Отмена не стирает операции/подтверждения, не обнуляет историю клиента и не оживляет отозванный/истекший купон. Она не делает клиента автоматически новым или повторным посетителем.
- [x] Гонки «применение — отзыв», «применение — применение» и «отмена — отмена» проверены на реальной PostgreSQL.
- [x] В аудите видны автор, время и причина операции без клинических текстов или секретов.
- [x] Время операции задается сервером; срок купона проверяется на момент подтверждения. Ручное изменение времени и привязка к старому визиту не добавлены.
- [x] Автоматический расчет итоговой цены приема отсутствует; фиксируется согласованный номинал купона и факт применения.

## MVP-05 — бумажная и электронная карточка

Цель: можно выдать компактный бумажный купон либо отправить его изображение/ссылку; оба представления используют одну сущность.

Критерии приемки:

- [x] Номер удобно переписать от руки; UUID и длинный URL не занимают длинную строку на бумажной карточке.
- [x] Отображаются скидка, срок или бессрочность, существенные ограничения посещений/использований и текст условий без скрытой обрезки.
- [x] QR ведет на публичную страницу по UUIDv4, показывающую актуальные публичные условия/состояние.
- [x] Публичный просмотр не раскрывает клиента, контакты, историю применений или внутренние ID клиентов/операций и не позволяет применить купон.
- [x] Открытие, сканирование, печать и повторная отправка не изменяют счетчики.
- [x] Отзыв/истечение отражается при повторном просмотре; бумага не считается доказательством актуальности.
- [x] Проверены desktop/mobile и печатное представление. Отдельная сущность шаблона пока не создается.

## MVP-06 — результаты пилота

Цель: специалист видит, сколько купонов выдано, какие использовались и сколько клиентов пришло по ним.

Критерии приемки:

- [x] Раздельно отображаются выданные купоны, купоны хотя бы с одним действующим применением, число неотмененных применений и уникальные клиенты.
- [x] Отдельно можно посчитать уникальных клиентов с ручным подтверждением первого посещения при неотмененном применении. Эта метрика помечена как подтвержденная специалистом и не выдается за автоматически проверенное число новых посетителей.
- [x] История применений не представляется полной историей посещений; число визитов, посещения без купона и возвращаемость по ней не рассчитываются.
- [x] Отмены и отзывы корректно учитываются; сохраняется возможность посмотреть историю, а не только конечный счетчик.
- [x] При расчете доли использованных купонов числитель — число купонов, а не число применений многоразовых купонов.
- [x] Нет расчетов выручки, стоимости привлечения или сэкономленных рублей на основе исключенного поля `Цена ₽`.
- [x] Сквозной browser-сценарий включает создание/поиск искусственного клиента, применение и отмену купона с разными настройками. Ни на одном шаге не требуется запись визита или подключение внешней CRM.
- [x] На искусственных данных проверены поиск клиентов, подтверждение первого посещения и одного купона на прием, печать/QR и резервное копирование с восстановлением. Есть инструкция ручной проверки на рабочем месте. Реальный домен, принтер, рабочая резервная копия и production-развертывание проверяются отдельно оператором перед пилотом, а не объявляются выполненными этим PR.

## Подход к проверкам

Для функциональных изменений применять команды из `AGENTS.md` и соответствующих вложенных инструкций. Измененные сценарии проверяются поведением: backend-тесты, проверки ограничений на PostgreSQL и browser E2E. Каждый PR сообщает фактически выполненные проверки и ограничения окружения.

Нельзя считать безопасным последний лимит только потому, что одиночный запрос проходит: обязательны параллельные запросы. Проверять повторную отправку форм, возможные дубликаты клиентов, отсутствие обязательных ручных подтверждений и сохранение истории при отмене. Идемпотентность и лимиты не выдавать за автоматическое соблюдение одного купона на реальный визит; ручное подтверждение не является независимой проверкой личности или истории посещений.
