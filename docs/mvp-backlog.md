# План реализации купонного MVP

Статус всех задач ниже: **запланировано, не реализовано**. `MVP-01` и другие обозначения — идентификаторы разделов этого плана, не номера уже созданных GitHub issues. Продуктовые правила находятся в [спецификации](coupon-mvp.md).

Каждая задача выполняется отдельным PR с необходимыми изменениями backend, frontend, контракта и проверок. Не создавать все будущие таблицы и интерфейсы в первом PR. Слияние и серверное развертывание — отдельные действия в рамках явно выданного разрешения.

## MVP-01 — вход специалиста и кабинет

Цель: специалист входит в приложение, получает доступ к своему кабинету и может завершить сессию.

Объем:

- Ввести команду запуска версионированных миграций и первые таблицы только для учетных записей/сессий.
- Создавать первую учетную запись через явную административную команду; без фиксированного пароля в исходниках и открытой регистрации клиентов.
- Добавить вход, получение текущей сессии и выход в API и OpenAPI, экран входа и оболочку кабинета во Vue.
- Использовать серверные сессии с безопасным хранением пароля, сроком жизни, завершением при выходе и защитой изменяющих запросов от CSRF. Cookie и настройки разработки/HTTPS документировать.
- Ограничить попытки входа. Получать специалиста из проверенной сессии, не доверять переданному клиентом ID владельца.

Критерии приемки:

- [ ] Чистая БД поднимается командами README; повторный запуск миграций не повреждает данные.
- [ ] Корректные учетные данные открывают кабинет; ошибочные не создают сессию и не раскрывают секреты.
- [ ] Защищенный API недоступен без сессии; чужой ID в запросе не меняет область доступа.
- [ ] Выход и истечение сессии прекращают доступ, включая прямые API-запросы.
- [ ] Секреты не попадают в логи или клиентскую сборку; настройки cookie/CSRF и ограничения попыток проверены.
- [ ] Есть browser-сценарий «вход — кабинет — выход» и проверки существенных ошибок.

В этот PR не входят купоны, пациентские данные, интеграция CRM и публикация реального сервиса для пациентов.

## MVP-02 — минимальные данные CRM и импорт

Цель: найти клиента и выбрать его состоявшийся визит без повторного ручного ввода всей CRM.

Объем: таблицы связи с внешними ID пациентов/визитов, состояние импорта, интерфейс поиска и просмотра визитов, чтение разрешенных столбцов Google Sheets. Сначала проверить обработку на искусственных данных; способ предоставления доступа к настоящей таблице документировать отдельно, без учетных данных в репозитории.

Критерии приемки:

- [ ] Поля соответствуют точным заголовкам из спецификации. `Посещение`, `НУЖНО УТОЧНИТЬ`, `Цена ₽` не влияют на результат и не требуются для импорта.
- [ ] Клинические поля, исходные тексты, доход и дата рождения не сохраняются и не попадают в вывод ошибок.
- [ ] Повторный импорт и сортировка строк не создают дубликатов. Изменение имени/телефона сохраняет ту же связь по ID.
- [ ] Пустые/дублирующиеся ID, неизвестный пациент и неверная дата отражаются как ошибки качества, не как успешная полная история.
- [ ] Сбой или частичная загрузка не заменяет последний полный снимок. Видны время обновления и ограничения актуальности.
- [ ] Порядок первых визитов учитывает старую историю и текущий визит, а одинаковые даты без достаточного времени/порядка дают неопределенность.
- [ ] Задокументировано, как подтверждается покрытие истории и что происходит при устаревших данных. В неоднозначных случаях нет автоматического допуска к скидке первого посещения.
- [ ] Google Таблица не изменяется. Искусственные тестовые записи не выдаются за проверку настоящего подключения.

Для проверки реального подключения потребуется ссылка/ID таблицы и доступ на чтение. Это не блокирует MVP-01 и локальные тесты MVP-02.

## MVP-03 — создание и отзыв купонов

Цель: специалист создает купон, видит его условия и счетчики, находит по короткому номеру и при необходимости отзывает.

Критерии приемки:

- [ ] Есть процентная и фиксированная скидки, необязательные текстовые ограничения, срочный/бессрочный режим и оба типа допустимых посещений.
- [ ] Общий и персональный лимиты независимо принимают положительное число или неограниченность. Персональный по умолчанию равен 1.
- [ ] Купон самостоятельный: нет сущностей программы лояльности или кампании.
- [ ] Создаются короткий номер и случайный UUIDv4. Ручные бумажные номера проверяются на допустимость и уникальность; старые номера не переиспользуются.
- [ ] Поиск, просмотр и отзыв изолированы по специалисту; массовый перебор ограничивается по инициатору запросов.
- [ ] Отзыв окончателен и не уничтожает историю. Поиск и просмотр купона не расходуют лимиты.
- [ ] До завершения задачи определены формат короткого номера, граница срока/часовой пояс, точность номинала и необходимость связи с рекомендателем. Выбранные решения явно отражены в спецификации и UI.

## MVP-04 — применение и отмена

Цель: после реального визита специалист подтверждает применение купона; ошибку можно отменить с причиной и сохранением истории.

Критерии приемки:

- [ ] Проверяются существование визита, его пациент и специалист, отзыв, срок, общий/личный лимиты, допустимость посещения и актуальность нужной истории.
- [ ] Не более одного действующего применения любого купона на визит обеспечивается в БД.
- [ ] При конкурентных запросах лимиты не превышаются, включая персональный лимит при неограниченном общем.
- [ ] Повтор одного запроса создает одну операцию. Одинаковый ключ с разными данными отклоняется; повтор после отмены не создает новую операцию самопроизвольно.
- [ ] Отмена освобождает оба лимита ровно один раз. Другой купон можно применить к визиту только после явной отмены прежнего применения.
- [ ] Отмена не удаляет визит, не обнуляет историю клиента и не оживляет отозванный/истекший купон.
- [ ] Гонки «применение — отзыв», «применение — применение» и «отмена — отмена» проверены на реальной PostgreSQL.
- [ ] В аудите видны автор, время и причина операции без клинических текстов или секретов.
- [ ] Перед реализацией определена политика старых визитов/визитов до выдачи купона; она не обходится выбором произвольного ID из старой истории.
- [ ] Автоматический расчет итоговой цены приема отсутствует; фиксируется согласованный номинал купона и факт применения.

## MVP-05 — бумажная и электронная карточка

Цель: можно выдать компактный бумажный купон либо отправить его изображение/ссылку; оба представления используют одну сущность.

Критерии приемки:

- [ ] Номер удобно переписать от руки; UUID и длинный URL не занимают длинную строку на бумажной карточке.
- [ ] Отображаются скидка, срок или бессрочность, существенные ограничения посещений/использований и текст условий без скрытой обрезки.
- [ ] QR ведет на публичную страницу по UUIDv4, показывающую актуальные публичные условия/состояние.
- [ ] Публичный просмотр не раскрывает клиента, контакты, историю применений или внутренние ID CRM и не позволяет применить купон.
- [ ] Открытие, сканирование, печать и повторная отправка не изменяют счетчики.
- [ ] Отзыв/истечение отражается при повторном просмотре; бумага не считается доказательством актуальности.
- [ ] Проверены desktop/mobile и печатное представление. Отдельная сущность шаблона пока не создается.

## MVP-06 — результаты пилота

Цель: специалист видит, сколько купонов выдано, какие использовались и сколько клиентов пришло по ним.

Критерии приемки:

- [ ] Раздельно отображаются выданные купоны, купоны хотя бы с одним действующим применением, число неотмененных применений и уникальные клиенты.
- [ ] Повторные посещения не называются новыми клиентами. Количество новых клиентов выводится только при подтвержденной истории первого визита.
- [ ] Отмены и отзывы корректно учитываются; сохраняется возможность посмотреть историю, а не только конечный счетчик.
- [ ] При расчете доли использованных купонов числитель — число купонов, а не число применений многоразовых купонов.
- [ ] Нет расчетов выручки, стоимости привлечения или сэкономленных рублей на основе исключенного поля `Цена ₽`.
- [ ] Сквозной browser-сценарий проходит с искусственными клиентами/визитами и разными комбинациями настроек купона.
- [ ] Перед реальным пилотом проверены доступ к CRM, ее полнота/актуальность, резервное копирование и работа специалиста с бумагой. Production-развертывание выполняется отдельным явным действием.

## Подход к проверкам

Для функциональных изменений применять команды из `AGENTS.md` и соответствующих вложенных инструкций. Измененные сценарии проверяются поведением: backend-тесты, проверки ограничений на PostgreSQL и browser E2E. Каждый PR сообщает фактически выполненные проверки и ограничения окружения.

Нельзя считать безопасным последний лимит только потому, что одиночный запрос проходит: обязательны параллельные запросы. Нельзя считать работающей интеграцию CRM только по импортированным искусственным данным: проверку настоящего чтения фиксировать отдельно после получения доступа.
