# Развертывание

## Модель

Один Linux amd64 сервер с Docker Engine и Compose v2.24+. Публичны только Caddy на 80/443. API и PostgreSQL доступны внутри сети Compose. Caddy получает TLS-сертификат и хранит его в именованном томе. Это базовое развертывание на одном сервере: возможен короткий перерыв при обновлении.

Production-конфигурация — самостоятельный `deploy/compose.yaml`. Не объединяйте ее с корневым Compose: корневой файл предназначен для локальной разработки и публикует порты API/БД.

## Публикация образов

CI на PR проверяет backend, frontend, контейнерный стек, восстановление после отказа БД и браузер. Только успешная сборка `main` публикует:

- `ghcr.io/azamatbayramov/referflow-api`
- `ghcr.io/azamatbayramov/referflow-web`

Оба образа имеют тег `sha-` + полный SHA одного коммита. Тег `latest` не используется. До первого успешного workflow на `main` production-образов нет. При создании пакеты GHCR могут быть приватными: настройте их видимость или выполните `docker login ghcr.io` на сервере с учетными данными для чтения пакетов. Токен в репозиторий не записывается.

Сборка образов на PR не публикует их и не запускает серверное развертывание. Публикация рассчитана на `linux/amd64`; локальные Docker-сборки работают на нативной архитектуре, включая Apple Silicon.

## Первый запуск

1. Направить DNS выбранного домена на сервер и открыть TCP 80/443; UDP 443 нужен для HTTP/3.
2. Клонировать репозиторий, переключиться на проверенный коммит из `main`.
3. Создать конфигурацию с правами только для владельца:

```bash
umask 077
cp deploy/.env.production.example .env.production
openssl rand -hex 32
```

4. В `.env.production` указать настоящий `SITE_ADDRESS` без схемы и пути, `IMAGE_TAG` из успешного workflow и сгенерированный `PGPASSWORD`. Секреты не передавать в PR. Пустые обязательные значения останавливают Compose до запуска.
5. Запустить и проверить:

```bash
make deploy
make production-logs
```

`make deploy` валидирует конфигурацию без печати секретов, сначала загружает все образы, затем применяет ее и ждет health checks. После запуска проверить `/`, `/api/healthz` и `/api/readyz` по HTTPS на своем домене. Внутренняя проверка Caddy подтверждает работу процесса; публичный DNS и получение сертификата проверяются отдельно.

На сервер ничего не отправляется автоматически: адрес сервера, домен и секреты оператор задает при первом реальном развертывании.

## Обновление и откат

1. Дождаться успешной публикации обоих образов нового коммита.
2. Записать предыдущий `IMAGE_TAG`, сохранить резервную копию БД и текущей конфигурации.
3. Обновить checkout до того же коммита, установить новый `IMAGE_TAG` и запустить `make deploy`.
4. Проверить публичные health endpoints и приложение. Ошибка `--wait` завершает скрипт с ошибкой, но не выполняет автоматический откат.

Для отката вернуть предыдущий checkout и `IMAGE_TAG`, затем повторить `make deploy`. Тома не удалять. Откат приложения безопасен только при совместимой схеме БД; когда появятся миграции, каждой задаче нужно явно описывать совместимость и порядок восстановления.

## Резервная копия и восстановление

Пример ручной резервной копии из корня checkout на сервере:

```bash
umask 077
mkdir -p backups
docker compose --env-file .env.production -f deploy/compose.yaml exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "backups/referflow-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Хранить копии вне сервера и периодически проверять восстановление. Каталог `backups/` исключен из Git. Архивы могут содержать персональные данные, когда они появятся в продукте.

Восстановление сначала проверяют на отдельной пустой БД того же major PostgreSQL: остановить запись приложением, подать выбранный архив на stdin команды `pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --exit-on-error --single-transaction`, затем проверить схему и данные. Не выполнять восстановление поверх рабочей базы без отдельного плана замены. Содержимое томов PostgreSQL нельзя копировать во время записи как обычные файлы.

`docker compose down` сохраняет тома. `down --volumes` удаляет БД и сертификаты. Не использовать эту опцию в production. Пароль существующего пользователя меняется в PostgreSQL отдельно от переменной в `.env.production`.

## Эксплуатационные границы

Логи направлены в stdout/stderr; Docker ограничивает их размер. API работает от непривилегированного пользователя с read-only файловой системой. Постоянные данные находятся в PostgreSQL-томе, сертификаты — в Caddy-томах. До реальных закрытых операций требуется отдельная реализация авторизации; никаких таких операций этот PR не добавляет.
