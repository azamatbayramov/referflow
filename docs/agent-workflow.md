# Разработка с агентами

## Одна задача — один проверяемый результат

Заводите задачу через `.github/ISSUE_TEMPLATE/task.yml`: цель, границы, критерии приемки и зависимости. Агент начинает с `AGENTS.md`, нужной документации и просмотра текущего кода, затем работает в отдельной ветке. Описание PR должно соответствовать итоговому изменению.

Пример готового запроса для небольшой инфраструктурной задачи:

> Добавь ограничение размера HTTP-запроса в API. Сначала прочитай AGENTS.md и backend/AGENTS.md. Ограничение должно задаваться конфигурацией, неверное значение должно останавливать запуск с понятной ошибкой без секретов. Слишком большой запрос должен возвращать JSON с HTTP 413. Добавь тесты граничного размера и превышения, обнови контракт и документацию конфигурации. Не добавляй бизнес-endpoints, используй тестовый handler для проверки middleware. Запусти проверки backend и открой PR с фактическими результатами.

## Порядок работы

1. Проверить `git status`, актуальную базовую ветку и инструкции в затронутых каталогах.
2. Уточнить критерии успеха. Если API меняется, сначала согласовать контракт между frontend/backend.
3. Реализовать ограниченный объем задачи вместе с проверкой результата. Не реорганизовывать соседние части без причины.
4. Запустить проверки затронутой области; для конфигурации запуска — полный стек и smoke/E2E.
5. Проверить итоговый diff, отсутствие секретов и соответствие документации.
6. Открыть PR: проблема, получившееся поведение, проверка, эксплуатационные изменения. Разделить выполненные и недоступные проверки.

## Независимые рабочие каталоги

Если несколько исполнителей работают одновременно, назначить непересекающиеся области и отдельные worktree. Например, из основного checkout:

```bash
git fetch origin
git worktree add ../referflow-api -b feat/api-foundation origin/main
git worktree add ../referflow-web -b feat/web-foundation origin/main
```

У каждого worktree свои `.env`, зависимости и порты. Для параллельных локальных стеков задать разные `COMPOSE_PROJECT_NAME`, `WEB_PORT`, `API_PORT`, `PGPORT`. Изменения общего контракта, lock-файлов, Compose и CI должен координировать один владелец задачи. Не запускать несколько агентов на одном наборе изменяемых файлов.

## Проверка результата и передача

Проверяющий читает diff относительно `main` и сверяет поведение с критериями, особенно ошибки, совместимость API, секреты и восстановление после сбоев. Передача включает ветку/PR, сделанный объем, точные команды проверки, известные ограничения и оставшиеся зависимости. Фраза «должно работать» не заменяет запуск проверки.

Правила не зависят от конкретной модели или редактора. Если инструмент не читает `AGENTS.md` автоматически, укажите файл в первом запросе. Ключи моделей хранятся в настройках инструмента, а не в репозитории. Автоматические проверки помогают ревью; слияние и production-развертывание выполняются только в рамках отдельного разрешения на эти действия.
