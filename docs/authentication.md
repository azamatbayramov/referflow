# Вход специалиста

Реализованы вход, текущая сессия, выход и кабинет с профилем. Доступны [карточки клиентов](clients.md); купоны и их применения пока не реализованы. Публичной регистрации и выдачи учетных данных через веб-API нет.

## Локальный запуск

```bash
make up
make create-user
```

Команда спрашивает логин, имя и пароль. Пароль содержит 8–128 Unicode-символов, допускает пробелы и не требует определенных типов символов. Ввод скрыт; пароль передается команде `manage create-user` через stdin, не через аргумент процесса, файл или переменную `VITE_*`. Логин не требует адреса почты: 1–254 Unicode-символа без пробелов внутри, управляющих и невидимых форматирующих символов. Пробелы по краям удаляются, регистр не учитывается. Повторный логин не создает второй аккаунт. Email отдельно не собирается и не возвращается в API.

Для разработки без контейнера API:

```bash
make setup
make db
make migrate-host
make create-user-host
make dev-api
```

В другом терминале — `make dev-web`. Содержимое `.env` доверенное: команды Make читают его как shell-файл. Если вы меняете порт web/Vite, добавьте точный origin с этим портом в `APP_ORIGINS` и перезапустите API.

## Сессия и защита запросов

- Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, случайная соль 16 байт, ключ 32 байта; формат хранит алгоритм и параметры. Используется `crypto/pbkdf2` стандартной библиотеки Go без новой зависимости. Это сознательный выбор стандартной реализации; при пересмотре политики можно добавить новую версию формата, сохранив проверку старых хешей.
- Токен сессии: случайные 32 байта; в БД хранится только SHA-256 токена. В JSON токен не возвращается и в localStorage/sessionStorage не записывается.
- Production cookie: `__Host-referflow_session`, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, без `Domain`. Для явного HTTP на loopback — `referflow_session` без Secure. Небезопасные origins вне loopback отклоняются конфигурацией.
- Срок абсолютный, по умолчанию 12 часов; `SESSION_TTL` допускает 1m–168h. Каждый защищенный запрос проверяет срок в PostgreSQL. Перезапуск API не сбрасывает сессии. Новый вход меняет токен и отзывает старую сессию из переданной cookie.
- POST требует точного разрешенного `Origin`. Logout дополнительно требует `X-CSRF-Token` из login/session; токен связан с текущей сессией. Отсутствующие/чужие origins и CSRF отклоняются. SameSite используется как дополнительная защита, CORS-доступ не выдается.
- API определяет владельца из сессии. ID в query/body не позволяет выбрать другого специалиста. Ошибки не содержат пароли, SQL, адрес БД или токены; ответы сессии и ошибок имеют `Cache-Control: no-store`.
- Logout удаляет сессию на сервере и очищает cookie. При недоступной БД возвращается 503: API не заявляет успешного выхода и сохраняет возможность повторить его. После фактического отзыва старая cookie дает 401.

## Ограничение входа

PostgreSQL хранит бюджеты попыток, общие для всех экземпляров API: до 10 попыток на нормализованный логин за 15 минут и до 120 попыток на приложение за минуту. Учитываются успешные и неуспешные попытки, существующие и неизвестные аккаунты. В ключе счетчика хранится хеш логина. Окно начинается с первой попытки, повторные ошибки не продлевают его. Устаревшие счетчики удаляются при следующем входе.

При превышении — 429 и консервативный `Retry-After: 900`. Глобальный бюджет защищает от перебора разных адресов и ограничивает рост таблицы. Цена такой простой защиты: направленные попытки могут временно затруднить вход известному аккаунту; глобальный бюджет относится ко всему небольшому приложению. По результатам пилота лимиты можно пересмотреть. Поддельные `X-Forwarded-For` не обходят эту схему, поскольку она не доверяет IP из запроса. Одновременно на процесс выполняется не более четырех проверок пароля; при перегрузке — 503.

Неизвестный логин проверяется против случайного фиктивного хеша той же стоимости и получает такое же сообщение 401, как неверный пароль существующего аккаунта. Тело входа ограничено 4096 байтами; допускается один JSON-объект без неизвестных полей.

## Миграции

`manage migrate` применяет встроенные SQL-файлы в транзакции под PostgreSQL advisory lock. `schema_migrations` хранит имя, контрольную сумму и время. Повторный запуск ничего не дублирует; изменение примененного файла останавливает миграцию. API самостоятельно схему не меняет; до миграции readiness возвращает 503.

Миграция 001 добавляет `specialists`, `sessions` и `login_limits`. В ней нет клиентов, купонов или визитов. Изменение аддитивное, прежний инфраструктурный каркас может работать с этой БД; при откате приложения таблицы сохраняются. Автоматического удаления схемы/down-команды нет.

Миграция 002 переименовывает `specialists.email` в `login`, сохраняя ID, пароли, сессии и счетчики входа. Если вы уже создали аккаунт с email, этот адрес остается его логином. Примененный файл 001 не меняется. API теперь принимает `login` вместо `email`, CLI — `--login` вместо `--email`; миграцию, API и frontend нужно обновлять вместе. Откат к прежней версии авторизации с колонкой `email` требует согласованного восстановления БД и приложения, простого отката образа недостаточно.

## Production

`make deploy` сначала получает образы, запускает БД, выполняет миграции один раз, затем запускает новую версию API/web. `SITE_ADDRESS` задает точный HTTPS origin; Secure cookie включена всегда. Перед обновлением нужна резервная копия по [инструкции](deployment.md).

Для создания специалиста на сервере после запуска, из корня checkout:

```bash
read -r -p 'Логин: ' account_login
read -r -p 'Имя: ' account_name
read -r -s -p 'Пароль (8–128 символов): ' account_password
printf '\n'
printf '%s\n' "$account_password" | docker compose --env-file .env.production \
  -f deploy/compose.yaml exec -T api manage create-user \
  --login "$account_login" --name "$account_name" --password-stdin
unset account_password
```

Не включать shell tracing (`set -x`) при работе с учетными данными. Создание аккаунта — явная административная команда. Сброс пароля, самостоятельная смена пароля, MFA и управление сотрудниками через UI остаются за пределами этого этапа.

## Проверки

- `make check`: форматирование, lint, типы, unit-тесты с race detector и сборки обоих Go executables/Vue.
- `make test-integration` с заданным `TEST_DATABASE_URL`: выделенная тестовая PostgreSQL. Тесты создают случайные изолированные схемы; проверяют повторные/конкурентные миграции, контрольные суммы, аккаунты, срок/отзыв/ротацию сессий, откат неуспешной ротации и конкурентное ограничение входа.
- `make e2e`: работающий disposable Compose-стек, desktop/mobile Chromium. Проверяет вход, неправильный пароль, reload, принадлежность сессии, CSRF, выход, повтор старой cookie, истечение и ограничения входа. Случайные тестовые аккаунты не содержат реальных данных. Не запускать эти тесты на production.
- Для локального native-стека: `E2E_MANAGE_BIN`, `E2E_PSQL_BIN`, `BASE_URL`, `PG*`; при наличии готового Chromium доступен `E2E_CHROMIUM_PATH`. В CI используется стандартный путь Compose/Playwright.

Ориентиры: [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Go crypto/pbkdf2](https://pkg.go.dev/crypto/pbkdf2).
